  - docs(search): `successor_of` and `superseded_versions` are no longer described as the

    description, the skill and the README).
  - fix(mcp): lean ranked hits drop `chain_key` only for the chain that was searched
    (the requested one, or the server's default when none was given). A hit from a
    branch's ancestor, or a cross-chain replacement living on another chain, keeps its
    key even when every hit shares it; the old rule elided any key all hits shared.
  - fix(mcp): lean provenance fails closed. A lean thought that arrives with no
    provenance is marked `provenance: {"unknown": true}` instead of passing for the plain
    public, unsigned case, and every lean search response carries one
    `default_provenance` field saying what an unmarked hit is ("public, unsigned:
    anyone could have written it").
  - fix(search): cross-chain redirection could shrink a REST page. Ranked search (the
    chain and its ancestors) and federated search cut each chain's page at
    `offset + limit` before redirecting hits to a replacement on another searched chain
    and removing duplicate ids, so thirty ancestor facts replaced by one branch thought
    left a page of one hit. The fetch now doubles until the page is full or the matches
    are exhausted, up to `max(16 * (offset + limit), 4096)` per chain (a page whose live
    matches lie beyond that comes back short). `query_federated` in the library still cuts
    each chain at `limit`.
  - perf(search): refilling a page after near-duplicate collapsing is incremental and
    bounded. Each refill pass used to re-materialize and re-tokenize the whole window and
    the window had no limit; with 20% identical matches, collapse 0.9 and limit 10 a
    search cost 7.8 ms at 20,000 thoughts and 32.5 ms at 100,000. The walk now resumes where it stopped, compares
    only new hits with the survivors, merges same-text hits without tokenizing them, reads
    ranks with a lazy partial sort and memoizes lineage lookups: 1.2 ms and 3.5 ms. The
    window is capped at `max(16 * limit, 4096)` ranked slots, so a page whose distinct
    matches lie beyond that comes back short (remaining limitation).
  - fix(search): REST paging repeated and skipped hits around contested thoughts.
    A contester stands in at its contested thought's score plus a bump, so page order was
    not score order, and the REST ranked and federated handlers (which fetch
    `offset + page`, re-sort by score and skip `offset`) moved contesters between
    windows: 30 contested decisions paged by 5 returned 60 hits, 44 distinct. Emitted
    totals are now non-increasing in page order. Chains without lineage or contests are
    unaffected.
  - feat(mcp): lean output for agents. The streamable-HTTP MCP surface (JSON-RPC
    `tools/call`) returns minified JSON text and no second `structuredContent` copy
    (the MCP library pretty-printed the object and repeated it); `POST /tools/execute`
    and REST are unchanged. `mentisdb_ranked_search`, `_federated_search`,
    `_lexical_search` and `_context_bundles` are compact by default over MCP

    out defaults: no `provenance` for a public unsigned thought (private segment,
    signature and `verified_agent` are still listed), no `role: Memory`, no
    `importance: 0.5`, no `chain_key` for the searched chain, rounded floats, whole-second
    timestamps, `successor_of` reduced to the immediate predecessor plus a
    `superseded_versions` count, and the relation it names not repeated. Version status,
    successors and a verified writer are kept. `mentisdb_standing_context` returns the
    rendered `prompt` once; `entries` (a second copy of the same memories) needs

    went from 23,657 to 5,808 characters and standing context from 36,191 to 13,050.
    `cargo run --release --example token_diet` reproduces the numbers; the rules are in
    the `mentisdb::server_lean` rustdoc.
  - fix(search): superseded versions starved live results. `MentisDb::query_ranked`
    (ranked, lexical and federated search, and the seeds of context bundles) ranked a
    fixed window of `2 * limit` thoughts that included superseded ones, then collapsed
    them into their live successor, so one decision rewritten 30 times filled the window
    and a `limit = 5` search returned a single hit while `total` counted 21. Only live
    memories now compete for the page: every match is scored once, superseded ones
    nominate their live successor, and the walk stops when the page holds `limit`
    distinct live memories. `total` still counts live matches. Near-duplicate
    collapsing refills its page the same way instead of guessing a window.

  - feat(server): the minimum request-body rate is configurable.
    `MENTISDB_MIN_BODY_BYTES_PER_SEC` (default 65536; `0` switches the rule off;
    validated at startup like the other body limits) and
    `MentisDbServiceConfig::with_min_body_bytes_per_sec`. The fixed 64 KiB/s rejected
    imports over slow links, and a busy server that polls a body late could look slow
    too.
  - security(server): the minimum transfer rate could be pre-paid. It compared the
    whole body's byte count with the time past the grace period, so a client that sent
    63 MiB at once could then trickle for about 16 minutes while holding a 64 MiB
    reservation. The rate is now judged per window (one idle timeout long, from the end
    of the grace period), each window on its own bytes, so credit cannot be banked: the
    trickle fails with `408` at the end of the first window.
  - fix(server): a request body cut off by the body limits (stalled, too slow, or
    over the in-flight budget) is `408` or `503` with `Retry-After` on every route,
    also with bearer-token access off. Handlers' own JSON extractors used to turn it
    into a generic `400`; the admission layer now replaces a client-error response
    with the real cause when it was the one that stopped the body.
  - security(server): a body could hold the large pool indefinitely by declaring
    64 MiB and sending a byte every 29 s: the idle timer restarts on every chunk and
    large bodies had no total deadline. Every body (large ones too) must now average
    at least 64 KiB/s (`MIN_BODY_BYTES_PER_SEC`) once its grace period (twice the idle
    timeout, 60 s by default) is over, otherwise it fails with `408`. A genuinely
    slower link than 64 KiB/s (about 0.5 Mbit/s) cannot upload a body for longer than
    the grace period.
  - security(server): anonymous request bodies no longer share a pool with
    authenticated traffic. Bodies from a caller with no valid token (bearer-token

    charges).

    declared length, with a per-peer share (2x the cap) and at most four large bodies
    per peer; every other request is charged only for the bytes that actually arrive,
    from a fixed 64 MiB pool with no per-peer limit (on a loopback bind every local agent
    is one peer), and an anonymous peer (bearer on, no valid token) may hold 8 MiB of it.

    body has been read, and small and anonymous bodies get a total deadline of twice the

    `0600`, and restored files are `0600` (Unix; no-ops elsewhere). Existing files and
    directories are never chmod'ed silently, except files MentisDB itself rewrites
    (temp file plus rename, so they become `0600`) and a backup archive it overwrites.

    with the `chmod 700` fix (`mentisdb::paths::data_dir_mode_warning`). Backups still
    exclude `operator/operator.key` (owner decision): `backup` and `restore` now print a
    reminder to back it up separately, and the CLI help, README and
    docs/CHAIN_ACCESS.md say so. Upgrade note: existing directories keep their mode; run
    `chmod 700 <data dir>` and `chmod 600` on the files you want private.
  - security(docker): the daemon now says so when it is reachable from other machines

  - security(read-auth): a flood of self-signed read proofs could lock every honest
    reader out of private chains. A proof verifies against the key written in its
    own header, so any fresh keypair made a valid one, and each was written into the
    100 000-entry replay cache before any authorization; once full, every genuine
    proof was refused with `503`, and behind one NAT those refusals also exhausted
    the shared invalid-proof budget (`429`). The nonce is now spent only when a proof
    is about to grant access to a private segment (once per request), so a key no
    chain authorizes, or a request that touches no private chain, never reaches the
    cache. The cache is also capped per key (25 000 of 100 000) and drops expired
    entries from an ordered queue instead of rescanning on every refusal. Behavior
    change: a proof refused by a full cache, or one that loses a race for its nonce,
    now reads the public view (as documented) instead of `503`; malformed, stale,
    badly signed and already-spent proofs still get `401`. Spent nonces are looked
    up without being recorded, so the check costs unauthorized keys nothing.
  - security(standing): stored text could forge the standing-context block loaded
    at session start. Content and agent labels were concatenated raw, so a thought
    containing line breaks could close the `=== STANDING CONTEXT ===` block early,
    add a `SYSTEM:` line and print a fake `[#n] Constraint/...` entry, ranked first
    by a writer-supplied importance of 1.0. Every rendered entry is now a single
    line: line breaks, control and invisible characters (bidi overrides, zero-width,
    tag characters) in content, agent ids, display names, owners, tags and concepts

    `registration_signature_hex`). BREAKING for clients that registered keys
    without a proof; `MentisDb::add_agent_key` gained a `&KeyRegistrationProof`.
  - fix(security): thought signatures were stored but never verified. A thought
    that carries a signature must now verify against an active, unrevoked key of
    its agent or the append is refused (typed `AccessError`, HTTP 403), on every
    chain. A new v2 payload (`mentisdb/thought/v2`, see docs/CHAIN_ACCESS.md)
    covers every semantic field including entity type, scope and relation
    validity and is bound to the chain key and head hash, so a signed thought
    cannot be replayed onto another chain or position; v1 signatures stay
    readable (the version is recorded in the 64/65-byte stored signature) but are
    not accepted on restricted chains. Signed thoughts are committed exactly as
    signed (no automatic relations, `valid_at` or dedup edges).
  - fix(storage): a crash that left more than about 40% of the final record on
    disk made the chain refuse to open ("length prefix ... points past end of
    file but the following bytes hold a complete record"). The torn-tail check
    decoded the partial payload, and a prefix of a current-layout record parses
    as a complete record in the shorter legacy layout (its `prev_hash`/`hash`
    are read from the zero bytes of absent `None` tags). A partial payload now
    only counts as a complete record when it carries a 64-digit hex hash, so
    genuine tears are truncated and preserved as `.torn-*` while a corrupt
    length prefix over an intact record still fails open untouched. Found by a
    new test that cuts the last record at every byte.
  - fix(storage): a failed group commit kept its bytes in the writer buffer, so
    the writer's shutdown flush appended them a second time. After a full disk
    (partial write) or a failed `fsync` the chain file held a torn record
    followed by its duplicate, which no repair can read past. The buffer is now
    always cleared and a failed write is rolled back to the pre-commit length.
  - fix(storage): a forged length prefix inside a chain record (restored
    backup, imported or copied `.tcbin`) or inside a persisted HNSW graph made
    bincode attempt a `String`/`Vec<u8>` allocation of the claimed size and
    abort the whole process (`memory allocation of 1125899906842624 bytes
    failed`), a one-file denial of service for the daemon. Every bincode decode
    of untrusted bytes (thought records, skill registries, sidecar WAL,
    implicit-edge overlay, HNSW graphs) now runs under a decode budget
    (64 MiB per thought record, 1 GiB per derived file) and fails with
    `InvalidData` instead. The wire format is unchanged.
  - fix(storage): an append against a missing or stale vector sidecar embedded
    the whole chain synchronously under the chain's write lock (a failed embed
    made the very next append do it), contradicting the "opening a chain never
    embeds its history on the request path" guarantee. It now queues a
    single-flight background rebuild with the chain's own provider, keeps
    serving lexical and graph signals until the rebuild is adopted, and a failed
    embed schedules the repair immediately instead of waiting for another
    append. The managed provider is now shared (`Arc`) with the worker.
  - fix(storage): vector sidecar freshness only compared thought count and head
    hash, so a sidecar with the right count and head but missing entries read as
    fresh and left those thoughts findable only lexically. Freshness now also
    requires one entry per thought and reports a gap as `StaleThoughtCount`.
  - feat(recall): agents no longer forget older memory at session start. The
    mandatory startup loaded only the last 12 thoughts, so a preference stated
    months ago was never loaded and users had to repeat themselves. New
    `MentisDb::standing_context` (module `standing`), MCP tool
    `mentisdb_standing_context`, REST `POST /v1/standing-context` and CLI
    `mentisdb thought standing` return the durable half of memory regardless
    of age: live Constraint, PreferenceUpdate, UserTrait, RelationshipUpdate,
    Goal, Decision and LessonLearned thoughts (user-scoped or unscoped), ranked
    by importance then recency, near-duplicate restatements collapsed
    (Jaccard >= 0.85, newest kept), capped per type (8) and in total (40), plus
    the newest Handoff and Checkpoint/Summary. Additive: no existing tool
    changed. Criterion bench `standing_context` (10k thoughts).
  - docs(skill): MENTISDB_SKILL.md startup now loads `mentisdb_standing_context`
    before `mentisdb_recent_context`, and a new RECALL TRIGGERS section (the
    read-side twin of WRITE TRIGGERS) tells agents to search before answering
    about past preferences, decisions and constraints, or when the user says
    "again" / "remember" / "last time". `initialize` instructions, the
    bootstrap tool description, README, WHITEPAPER 8.4 and CLI_PARITY follow.
  - fix(storage): registry files claimed to be written through a synced temp
    file but were only flushed, so after a power loss the rename could land
    before the data and leave a zero-length registry. `MENTISDB_FSYNC=1` now
    syncs the temp file before the rename (default unchanged: a sync per
    registry per append costs milliseconds on macOS).
  - perf(storage): a managed vector sidecar compacted its snapshot every 32
    appends, and each compaction serialized and hashed the whole corpus three
    times (about 200 ms per pass at 10 000 thoughts x 384 dimensions, inside the
    chain write lock, plus a full-corpus JSON copy in memory), so append cost
    grew with the chain. The compaction threshold now scales with the corpus
    (`search::wal_compact_threshold`, 1/16 of the entries, at least 32), the
    integrity digest is streamed into SHA-256 instead of buffered (digest
    unchanged, pinned by a test), and the flush no longer recomputes the digest
    the append already rebased onto. Append with a 3 000 thought sidecar: 4.6 ms
    to 2.1 ms (`append_sidecar/local_sidecar_3000_base`).
  - perf(storage): with `auto_flush` (the default) every append rewrote and
    renamed the entity-type registry even for thoughts without an entity type;
    it is now persisted only when a thought names one.
  - perf(storage): automatic dedup re-tokenized (stemming and lemma expansion)
    the last 64 thoughts on every append, about 0.49 ms of pure repeated work
    per append at 40 words per thought. A self-validating sliding window now
    tokenizes each thought once (`benches/storage_paths.rs`,
    `dedup_tokenize_window64`); results are identical.
  - perf(search): `LexicalIndex::scan` allocated and zeroed O(documents) score,
    term-mask and restriction arrays per query. The arrays are now kept in a
    per-thread scratch (capped at 64 MiB) and only the touched positions are
    cleared on drop, so a rare one-term query on a 100 000 document index drops
    from 9.9 us to 1.8 us and a three-term query from about 1.8 ms to 0.93 ms;
    scores are identical.
  - feat(access): per-chain write access control. Policies `open` (default),
    `signed` and `allowlist` are stored as signed `AccessPolicy` governance
    thoughts in the chain (hash-chained, auditable) with a Merkle commitment to
    the key set, replayed on open; changes need a current governor's signature,
    and the first record bootstraps governance with a global token. New library
    API `MentisDb::{access_policy, set_access_policy, verify_signatures}`,
    module `mentisdb::access`, module `mentisdb::signing` (one documented
    `verify_ed25519_signature`, key validation, payload builders, Merkle root),
    thought type `AccessPolicy` (reserved), MCP tools `mentisdb_get_access_policy`,

  - feat(cli): `mentisdb chain access show|set|allow|deny|verify`,
