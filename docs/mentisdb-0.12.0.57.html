MentisDB 0.12.0.57 — Shared vectors, derived-state backlog, large signed requests

November 3, 2026

A short release that closes the open ends of 0.11.0.56. That release moved the implicit-edge scan off the write lock and said what it cost: a second copy of every vector (about 150 MB at 100,000 thoughts) and a queue with no cap. Both costs are gone, operators can now see how far derived state is behind, and signed requests are no longer capped at 1 MiB.

1. One copy of every vector

The background scanner now shares the sidecar's vectors instead of copying them, and its queue stores positions instead of vectors. At 100,000 thoughts, heap growth while appending fell from 239.2 MiB to 56.3 MiB, and peak process RSS in the same bench (100,000 × 384) from about 1,120 MiB to 970 MiB. At 20,000 thoughts it fell from 46.4 MiB to 11.9 MiB. A backlog now costs a few bytes however long it grows, never blocks an append and never drops an edge.

2. See what is still catching up

GET /v1/chains and the MCP chain listing report a derived_backlog per chain: embeddings in flight, parked or missing, and implicit edges not yet in the overlay. All zeros means healthy. A growing embedding count points at a stalling provider. A growing edge count means appends are faster than the scan (about 155 per second at 100,000 thoughts); the edges for the newest thoughts then arrive late and catch up when appends slow down.

Why 0.12

To share vectors, VectorSidecarEntry::vector became Arc<[f32]>. Code that embeds MentisDB and reads that field as a Vec needs .to_vec(); the release notes have a before-and-after snippet. The file format, the wire protocol and the CLI are unchanged, and no migration runs.
