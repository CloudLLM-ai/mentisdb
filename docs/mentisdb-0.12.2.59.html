MentisDB 0.12.2.59 — Steady MCP stream, safe appends, source episodes

November 12, 2026

A maintenance release. If you connect an agent to MentisDB over HTTP MCP, Claude Code included, this is the one to take: the MCP event stream no longer goes silent, so your client stops dropping and reconnecting to it. It also closes a way one oversized thought could make a whole chain unreadable, makes source_episode actually stored and searchable, and brings the dashboard's Settings screen and Markdown skill import up to what the daemon supports.

1. The MCP event stream stays alive

MCP clients open a long-lived GET / on the MCP port to hear about events. MentisDB wrote nothing on it until a tool call was broadcast, and most of the time nothing is. HTTP clients with an idle-body timeout took the silence for a dead connection: one user's Claude Code logged hundreds of SSE stream disconnected: TimeoutError lines in a session, a reconnect every minute, and a reconnect that met a brief network stall could leave MentisDB disconnected until restart (cloudllm#57).

The fix lives in cloudllm_mcp 0.4.1, the MCP library MentisDB is built on. After 15 seconds with nothing to send, the stream sends an SSE comment line, : keepalive. Clients ignore comment lines by specification, so nothing else changes, and a busy stream carries none. A MentisDB test now opens its own MCP stream on a paused clock and expects the keepalives, so this cannot come back unnoticed. Restart the daemon to get it; there is nothing to configure.

2. One oversized thought can no longer break a chain

A single thought record is capped at 10 MiB, but the cap was only checked when a chain was opened. An append over it was written, and the next start-up refused to load the chain at all. Ordinary REST and MCP requests are limited to 2 MiB, so the way in was the library and the large-body import routes, for a token holder. The append itself now fails with a 400 before anything reaches disk.

3. source_episode works

The README documents source_episode, a tag for the conversation or session a memory came from. REST and MCP appends accepted it and silently dropped it. It is now stored and returned, and it is an exact-match filter on search, ranked, federated and context-bundle search, over REST and MCP. Thanks to cgcardona for the fix (#27). The CLI has the same: 

mentisdb thought append ... --source-episode standup-2026-11-12
mentisdb search "deploy plan" --source-episode standup-2026-11-12

Commands whose route cannot apply the filter, such as lexical search and traversal, refuse the flag instead of quietly ignoring it.

4. Every setting on the Settings screen

The dashboard's Settings screen was missing 18 variables the daemon reads, among them the dedup threshold, auto-edge settings, request-body limits, fsync and the search defaults. The HTTPS ports were shown but refused on save, and five settings read only at start-up were labelled hot-reload. One catalog now drives the screen, and a test fails if the daemon ever reads a MENTISDB_* variable the catalog doesn't list.

5. Skills written for agent harnesses import whole

Skill files written for Claude Code, OpenCode and similar harnesses use standard YAML frontmatter: a folded description: > over several lines, - item lists for triggers. MentisDB read the description as just > and dropped the lists, so those skills arrived with nothing to search on. Block scalars and block lists are now read, and a multi-line description survives export and re-import. Thanks to faulknerpearce for the change (#26).

Upgrading

There is no migration and no library break. Restart the daemon after upgrading. If you embed cloudllm_mcp yourself, the keepalive is on by default; StreamableHttpConfig::with_sse_keepalive(None) turns it off. The release notes list every change. 

cargo install mentisdb --locked --force
# or
docker pull ghcr.io/cloudllm-ai/mentisdb:0.12.2.59
