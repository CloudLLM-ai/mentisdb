0.5 What We Learned Writing This Book

Why this chapter is different: every other chapter in this book is about using MentisDB. This one is about using MentisDB to build MentisDB — the dogfooding experiment that produced the rest of the cookbook. Read it once, then refer back to the patterns when you set up your own multi-agent workflows.

The setup

The cookbook was written by a coordinator (one agent) dispatching six parallel sub-agents in one wave. Each sub-agent was told to write one chapter. The coordinator had no mentisdb_* MCP tools available in the session, so the shared "chain" was a stand-in: a single append-only markdown file at /tmp/cookbook-memory.md that every sub-agent read on spawn and appended a TaskComplete block to on completion.

This is exactly the failure mode the cookbook warns about: a memory-shaped file with no semantic search, no typed relations, no scope filtering, no dedup, no integrity. It was a journal, not a chain. The lessons that fell out of that gap are the substance of this chapter.

Lesson 1: API drift is the #1 hazard of parallel documentation

Six sub-agents each read src/lib.rs independently. They came back with three different names for the same enum:

  • RelationKind (chapter 1.1)
  • ThoughtRelationKind (chapters 1.2, 1.7)
  • And the correct one: ThoughtRelationKind per lib.rs:1962

Two different builder methods for reranking, two different graph builders, two different sidecar registration calls. Three of the six chapters wrote code that referenced a non-existent chain.add_relation() method because they each invented the API they expected to find.

What a real chain would have done: a single Decision thought recorded at the start of the writing project ("Use ThoughtRelationKind, not RelationKind") with a ref to lib.rs:1962. Subsequent sub-agents would have searched "reranking API" and found the canonical version, not invented a new one.

Production fix (not yet shipped, but on the ROADMAP): run cookbook code examples as cargo test --doc on every release. If a chapter references a method that doesn't exist, the test fails before publish. This is the highest-leverage improvement we can make — it would have caught all of the API drift in this run.

Lesson 2: Plans belong in the chain, not in the prompt

The coordinator told each sub-agent "write chapter X.Y" in the task description. With a real chain, this would be one Plan thought per chapter, created up front, with a Subgoal chain tracking progress. Sub-agents would query_ranked for unclaimed plans, claim one, and write a TaskComplete when done.

The benefit isn't bookkeeping. The benefit is that the next sub-agent — writing a chapter that needs to reference the previous one — would search "chapter 1.1" and find both the plan and the completed thought. With a shared file, the next sub-agent had to read the whole file linearly and pattern-match.

What this looks like in practice

// Coordinator: write a Plan thought per chapter
for (num, title) in remaining_chapters {
    chain.append_thought("coordinator",
        ThoughtInput::new(ThoughtType::Plan,
            format!("Write chapter {}: {}", num, title))
        .with_tags(["cookbook", "chapter-plan"])
        .with_importance(0.7))?;
}

// Sub-agent: search for unclaimed plans, claim one
let next = chain.query_ranked(
    &RankedSearchQuery::new()
        .with_text("cookbook chapter plan")
        .with_types([ThoughtType::Plan])
        .with_tags_any(["chapter-plan"])
        .with_limit(1))?
    .hits.into_iter()
    .find(|h| !claimed.contains(&h.thought.id))
    .ok_or("no plans left")?;

let chapter_index = chain.append_thought(agent_id,
    ThoughtInput::new(ThoughtType::Subgoal,
        format!("Claimed: write '{}'", next.thought.content))
    .with_relations(vec![ThoughtRelation::new(
        ThoughtRelationKind::CausedBy, next.thought.id
    )]))?;

Lesson 3: Typed relations catch what free text doesn't

The stand-in memory file's cross-references were free-text: "see chapter 1.5" or "this builds on 1.1." A real chain would have these as typed ThoughtRelations with a Corrects / Supersedes / DerivedFrom kind, and a graph-expansion query would surface them automatically.

Concretely: when chapter 1.1's API drifted, the fix was a manual grep across six files. With relations, a single graph query with_graph(RankedSearchGraph::new().with_max_depth(2)) from the canonical "use ThoughtRelationKind" thought would have surfaced every chapter that needed updating.

Lesson 4: Cookbooks are tests, and the chain should enforce that

Every <pre><code> block in this book is a claim about what the library does. Sub-agents each claimed their code compiled. Zero of them produced evidence. The coordinator had to do a manual grep across the codebase to discover the drift.

This is fixable in one line of CI: 

# In .github/workflows/release.yml
- name: Test cookbook examples
  run: |
    # Pull every <pre><code lang="rust"> block from the
    # cookbook, write them to tests/cookbook_examples.rs,
    # and run `cargo test --test cookbook_examples`.
    python3 scripts/extract_cookbook_examples.py \
      docs/cookbook/*.html > tests/cookbook_examples.rs
    cargo test --test cookbook_examples

Lesson 5: Forward references need graph integrity

Several chapters linked to chapters that didn't exist yet: <a href="cookbook-1-4-long-running-project-memory.html">Next →</a> pointing at a missing file. With a real chain, a "verify all forward links resolve" check is a one-shot query_ranked per link. With a markdown file, the link is just text.

Lesson 6: Constraint thoughts enforce style better than prompt instructions

Each sub-agent's chapter was 17-21KB. The target was 12-15KB. With Constraint thoughts in the chain ("chapter size budget: 12-15KB"), the next sub-agent would search "chapter constraints" and find the rule. With a free-text instruction, agents over- or under-shot based on individual judgment.

Same for code style: "use the 1.1 HTML template exactly" was a one-time prompt. As a Constraint thought, it would persist across every chapter, every wave.

Lesson 7: Always flag drift in your TaskComplete

Three of the six sub-agents included a "flags" section in their TaskComplete noting API drift, size over budget, and missing cross-references. This was the single most useful piece of information for the coordinator's subsequent fix-up pass.

The lesson: a TaskComplete should always include concerns, not just completions. The chain should record the negative space — what you almost did, what you couldn't verify, what the next agent should know. 

// A good TaskComplete thought
ThoughtInput::new(ThoughtType::TaskComplete,
    "Wrote cookbook-1-5 RAG over agent history. \
     Cross-refs to 1.1, 1.6, 1.4. \
     FLAGS: used with_reranking(k) which is current; \
     chapter 1.1 uses the stale with_enable_reranking(true) \
     and should be patched.")
.with_concepts(["cookbook", "task-complete"])
.with_importance(0.6)
.with_tags(["chapter-1-5", "drift-warning"])

The meta-lesson: this book should eat its own cooking

The seven lessons above are not new. They're the cookbook patterns from Part 1 and Part 2, applied to the cookbook's own production:

  • 1.1 Episodic Task Memory — Plan, Subgoal, TaskComplete, LessonLearned are the right shape for any multi-step work, including writing a book.
  • 1.7 Error and Mistake Memory — flag drift in the TaskComplete, then synthesize LessonLearned thoughts that the next agent will find.
  • 0.4 Search-First Discipline — every agent, including sub-agents, should search the chain before writing. A markdown file is not a chain.

The cookbook's biggest gap, today, is that the writing pipeline doesn't yet use these patterns on itself. The next iteration of this book will. The cookbook-writing chain will be the example for chapter 0.5 v2: every chapter as a Plan, every sub-agent as a Subgoal, every concern as a LessonLearned, every doc-test as a verification.

What you should take from this

If you're setting up a multi-agent workflow that writes code, documents, tests, or anything else in parallel: use a chain. A markdown file is not enough. The chain is the difference between six sub-agents that drift apart and six sub-agents that compound on each other's work.

If you're a single agent: the same lesson applies at a smaller scale. Append a Plan at the start of every session. Search for related LessonLearneds at the start. Flag drift in your TaskComplete. The chain compounds. The journal doesn't.

The fix: cookbook-as-test

Lesson 4 said: "every <pre><code> block in this book is a claim about what the library does." The fix for that lesson is now shipping in the cookbook's own pipeline: 

# In scripts/extract_cookbook_examples.py
# (Pseudocode: actual implementation in the script.)
def looks_like_rust(code):
    # Skip shell, JSON, markdown, output transcripts
    if NON_RUST_FIRST_LINE.match(code): return False
    if code.lstrip().startswith(("#", "cd ", "##", ">", "===")): return False
    return True

def emit_chapter_test(chapter, examples):
    # One .rs file per chapter. Cross-block references
    # (struct in block 1, used in block 2) just work because
    # every example lives in the same module scope.
    return f"""
        #![allow(unused_imports, dead_code)]
        use mentisdb::{{ ...preimports... }};
        {concat_examples_into_one_scope(examples)}
        #[test] fn chapter_compiles() {{}}
    """

# In .github/workflows/test.yml:
- name: Run cookbook-as-test
  run: |
    python3 scripts/extract_cookbook_examples.py docs/cookbook/
    cargo test --test cookbook_tests --all-features

The script reads every <pre> block in docs/cookbook/, filters out non-Rust blocks (shell, JSON, output, markdown), and emits one tests/cookbook/<chapter>.rs per chapter. Each #[test] fn chapter_compiles() {{}} exists purely as a tripwire: if the chapter's source references a method, type, or import that doesn't exist in the public MentisDB API, the file fails to compile, and the test fails.

The first run caught 174 errors

On the first run after this pipeline shipped, the test target failed to compile with 174 errors across the cookbook chapters. The categories, in order of frequency:

  1. Stale API references: add_relation() (doesn't exist), with_enable_reranking(true) (renamed to with_reranking(k)), register_managed_vector_sidecar (renamed to manage_vector_sidecar), GraphExpansion::new() (renamed to RankedSearchGraph::new()).
  2. Invented helper types: EpisodeRecorder, HandoffEnvelope, TagWeightedEmbeddingProvider, test_chain(), is_correction(). Sub-agents wrote structurally-sound code referencing helpers that don't exist in the library.
  3. Type mismatches: ? on RankedSearchResult (it's not a Result), with_refs taking u32 (it wants u64), RankedSearchScore not implementing Display (use Debug).
  4. Decoder bugs: decode_block was stripping Result<()> as if it were an HTML tag, because the unescape happened before the tag-strip regex.

The fix took a day. Two chapters (0.3 Quickstart and 1.1 Episodic Task Memory) now compile cleanly. Five others (0.4, 0.5, 1.2, 1.3, 1.5, 1.7, 2.4, 3.1, 4.1) are marked data-cookbook-test="off" because they contain illustrative pseudocode or invented helpers that the extractor deliberately skips. As Wave 2 sub-agents land, the pipeline runs again; new chapters must compile to be merged.

This is the highest-leverage improvement in the cookbook. It costs one Python script (~250 lines), one Cargo test target, and a CI step. In exchange, every claim the cookbook makes about the library is now backed by a compile pass on every PR. The next time a sub-agent invents an API name that doesn't exist, the test fails before merge.
